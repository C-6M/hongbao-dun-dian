# 第二轮本地提速与人数显示

日期：2026-11-12，北京时间。新版已在本机运行。完整五分钟窗口内，红包请求中位耗时 268 → 84 毫秒，成功红包查询 282.8 → 285.4 次/分钟；吞吐增幅约 0.9%，改善主要体现在请求耗时和尾部延迟。

## 实现

- 每轮使用独立的 HTTPS 连接池，经原 HTTP 代理建立 CONNECT 隧道，同轮复用连接。建立连接期间也受并发上限约束；本轮结束、失败或风控中止时关闭连接，下一轮重新创建，避免请求沿用旧出口。
- 完成轮次或失败后，已有其他可用出口时等待 250 毫秒进入下一轮，减少原来的 8 秒空等。没有可用出口时仍按冷却和复用时间等待。
- 本地试跑开启一次出口检查 NETWORK 重试，共用原请求总预算。没有对 HTTP、业务或风控错误重试，也没有在连接池失败时自动调用 curl 重发。
- 红包表新增“在线榜人数”。来自 getOnlineGoldRank 的 onlineNum；接口提示“投喂、点赞、发弹幕均可上榜”，因此这是互动榜统计，不能用作真实抽奖参与人数。
- 每轮最多选择一个仍有电池红包、且余时至少 15 秒的房间补查。已有主播 UID 时 1 次请求，未知时最多 2 次，预先从本轮预算扣除；同房间成功或失败均至少间隔 2 分钟。实际刷新频率还受活动数量影响。
- 人数缓存随房间池保存；未知显示“待更新”，合法 0 保留为 0，旧数据显示年龄，悬停可看更新时间。人数不影响现有评分、排序和通知门槛。长期记录可以单独筛选人数和主播资料请求。

并发 5、至少 90 毫秒启动间隔、每节点每轮总请求不超过 110、至少 180 秒复用和风控冷却 15 分钟继续生效。

## 开关与备份

下次启动前设置 SCANNER_POOLED_HTTP=0，可恢复每请求 curl；SCANNER_ROOM_AUDIENCE=0 可停止人数补查。两者不会关闭上一轮已完成的 CPU 优化和 HOT 动态复查。SCANNER_SPREAD_BUDGET=0 仍可关闭分散派发与轮内替换。

当前本地启动使用 SCANNER_IP_NETWORK_RETRY=1；该选项仍需显式开启。代码和相关测试备份在 before/，停止时保存的节点和房间状态继续保留。回退代码时先正常停止扫描，保留现有数据，避免覆盖新产生的记录。

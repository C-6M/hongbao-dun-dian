# 重复启动与 Clash 控制器重连修复

2026-11-15，北京时间。

用户重复启动时，原扫描器 PID 15816 仍在后台持有本项目的锁。旧入口把正常的重复启动当成致命错误，批处理随后停留在按键提示。同时发现原进程主扫描已停在 `fetch failed`，成功扫描计数停留在 93,009；Clash 在 15:15 重启，当前配置中的控制器 `127.0.0.1:7158` 可以正常读取版本及节点。旧代码只在扫描器启动时探测控制器地址。

本次修改：

- 普通启动遇到存活的锁持有者时显示 PID 并正常返回，不再进入加载房间池、历史写入或扫描流程。有限轮次命令仍要求独占，停止命令仍传递给现有实例；无效锁保留并报错，已退出进程的锁可按原流程恢复。
- `1-启动扫描器.bat` 成功返回时直接关闭，失败时才保留按键提示。保留 UTF-8 无 BOM 与 CRLF 换行。
- Clash 控制请求发生传输错误时重新读取配置并验证控制器。仅在发现不同的有效地址后重试一次；HTTP 错误不触发重放，停止时取消请求，不重连。B 站扫描请求不经此路径重试。
- README 同步了启动与控制器恢复行为。

验证结果：

- 全量 Node 检查 282 项通过，见 `tests.tap`。
- 真实运行批处理和本地启动器重复启动，均返回 0，既有锁保持不变，不显示致命错误或按键等待；新版本启动后再次验证批处理也通过。
- 用独立的本地故障响应端模拟控制器失联，新代码成功从当前 Clash 配置找到 7158 端口、验证后重试并取得 HTTP 200。没有重启或修改用户的 Clash。
- 旧扫描器保存退出，新版本于 15:27:11 启动，持续运行的扫描器 PID 为 40864。
- 15:31:03 最终核对：成功扫描 1,705 次，新增 8 个红包（7 个电池包），网络错误和风控均为 0。原有 280 间 HOT/WARM 已全部复查，运行配置保留，每轮代理请求不超过 130 次。
- QQ 原进程保持运行并已就绪，原有 405 个发送/查重键全部保留。旧扫描会话在历史库中正常结束。

`before/` 保存修改前源码和批处理。`duplicate-start.json`、`controller-reconnect.json`、`after-startup.json`、`verified.json` 保存本次实际验证结果。新扫描日志位于 `data/scanner-startup-20261115.stdout.log` 和 `data/scanner-startup-20261115.stderr.log`。SQLite 的实验性功能提示仍可能出现，它不会使启动返回错误。

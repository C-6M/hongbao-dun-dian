# 网站重新上线后，为什么能搜到这么多

调查日期：2026-11-11，北京时间。

结论：这个网站确实有真实的红包来源和较广的当前覆盖。页面数量还包含大量礼物、亲密度及小额电池包。对我们最有价值的方向是恢复持续运行、提高活跃房间覆盖和接入及时的发现信号，单纯提高房间评分不足以缩短当前排队时间。

## 1. 当前数量要按同一口径比较

第一次接口快照时间为 21:09:17；接口报告本次进程启动于 20:43:55，版本为 `11-11 20:43`。

| 第一次快照 | 数量 |
|---|---:|
| 人气红包列表全部条目 | 49 |
| 电池红包 | 22 |
| 人均至少 10 电池、普通参与条件的电池包 | 0 |
| 天选条目，单独列出 | 18 |
| 出口节点，均报告健康 | 14 |

`min_price=0`，页面展示全部人气红包类型。49 条中其余 27 条是爱的抱抱、你真好看、告白花束、干杯、情书、棒棒糖和亲密度红包。我们的“人均至少 10 电池”是通知和高价值证据门槛，不是删除所有小包的显示规则；比较时要分别统计。

随后在本地时间 **21:10:31—21:13:31**，每 5 秒读取一次网站已经提供的公开状态，共 37 份快照：

| 三分钟观察 | 结果 |
|---|---:|
| 同时在列表中的人气红包 | 36—125 条 |
| 排除已过开奖时间的条目 | 36—124 条 |
| 同时有效的电池包 | 18—47 条 |
| 累计看到的不同人气红包 | 138 条 |
| 其中不同电池包 | 50 条，分布于 37 个房间 |
| 达到人均门槛、无显式特殊条件 | 4 条 |

138 条包括观察开始时已经存在的 37 条，不能表述为“三分钟新发了 138 个红包”。四个达到门槛的包均为 100 电池总额，名额 5/5/10/5，来自 `1726399870`、`1830538239`、`1950045879`、`1950886172`。

证据：`site-initial.json`、`site-000.json` 至 `site-036.json`、`analysis.json`。

## 2. 能确认的采集特点

**数据真实同源。** 抽查 8 个房间、14 个电池包，网站的红包 ID、总价值和结束时间均与 B 站 `RedPocketGetInfo` 返回一致。我们与它都能通过这个接口读取这些包，样本没有显示访问权限方面的差异。这不等于已经知道它全部后台数据来源。

**存在明显的批量发布。** 三分钟累计记录中，108 条首次出现时带 `scan=1`，30 条没有该字段；其中一次刷新增加了 90 条记录，90 条全部带 `scan=1`。这与轮询采集后集中更新状态的行为一致。公开接口没有后台扫描次数、并发或周期，无法据此计算它的实际请求速度。

**可能有另一种输入通道，但 WebSocket 尚未证实。** 一条不带 `scan` 的高人均包，在观察中首次出现时距官方 `start_time` 约 9 秒；另一条带 `scan=1` 的包约 353 秒后才首次出现。它可以及时获得某些新包，也会较晚补入另一些包。字段差异和时间差支持多种输入路径的推测；后台轮询任务差异、缓存合并、外部上报也可能产生这种现象。

旧的 `docs/红包站分析报告.md` 将“没有 src”“部分房间不在抽样列表里”直接写成已证明弹幕 WS 接入，证据不足。本次将 WS、全站扫描和具体代理轮换方式均保留为待验证假设。

**节点规模较大。** 当前公开响应含 14 个健康节点，我们配置上限为 8 个。若节点对应独立出口、采用相同预算，理论节点容量比为 14/8=1.75；但网站隐藏了实际 IP，节点数不能直接当作独立 IP 数或吞吐量。前端每 5 秒刷新也只代表展示频率。

证据：`official-validation.json`、`useful-validation.json`、`pool.html`、`analysis.json`。高人均包追加复核时，2 条仍有效并匹配，另外 2 条已经超过开奖时间，不能将它们当作接口不一致。

## 3. 我们当前更明显的瓶颈

**当前没有同期运行对照。** 本地状态最后更新于 **18:42:10**，保存的扫描器 PID 已不存在；网站的上述快照在 21 时之后。不能拿这两份页面直接判断网站命中率比我们高多少，也不能根据历史库中未关闭的 `running` 标记认为扫描器仍在运行。停机原因本次没有确认。

本地最近一次运行从 **15:13:34** 开始，最后一条成功红包查询约在 **18:41:42**。成功查询 58,245 次，约 **280 次/分钟**，覆盖 19,437 个不同房间；保存的总房间池为 **74,856** 个。

在本次运行内，同房间相邻两次成功查询都标为同一层级时，间隔中位数如下：

| 查询层级 | 实际间隔中位数 |
|---|---:|
| HOT | 约 30 秒 |
| WARM | 约 110 秒 |
| 固定历史来源 | 约 15.3 分钟 |
| 榜单冷扫 | 约 30.6 分钟 |
| 普通冷扫，包括低频房间 | 约 64.1 分钟 |

这些是实际相邻查询间隔，不是设置中的最短资格间隔；房间在两次查询之间可能离开或重新进入榜单。配置的“榜单最短 2 分钟”并不保证每个候选每 2 分钟都会查到。官方复核样本中的红包有效期为 5 或 10 分钟，排队时间足以让一整个包在两次查询之间结束。

当前网站的 37 个电池包房间中，20 个不在我们停机前保存的房间池里；另外 17 个已经在池内，其中 16 个在本地最后更新时间就已处于低频状态，且超过 6 小时没有查询。四个达到人均门槛的房间都不在保存的池里。

因此可以确认两类覆盖问题：历史房间入池后未及时复查，以及当前网站有额外的新房间线索。停机期间没有更新名单，20 个未匹配房间不能全部记作算法漏检；房间号匹配也按原始 ID 进行，没有全面验证短号别名。

证据：`local-run-analysis.json`、`room-pool-initial.json`、`local-initial.json`、`runtime-check.json`、`analysis.json`。

## 4. 建议按这个顺序优化

1. **恢复并验证持续运行。** 用真实进程、状态更新时间和请求增量判断是否工作；补充异常原因记录，避免看板长期显示旧池。先取得同一时段的比较样本。
2. **给活跃房间和首次发现保留及时查询机会。** 已有 7.5 万房间不应共同决定有效包的发现延迟。按剩余查询预算反推可在 2—5 分钟内覆盖的候选数量，将刚开播、刚进入列表、近期红包证据单独纳入有界的首次查询/复查队列。保留原请求上限，并用实际等待时间检验。
3. **将全站 TOP50 与分区榜的覆盖分别验收。** 共用 20% 上限时，单列 TOP50 的最长等待和未查比例，必要时在原榜单预算内分配份额。四个高人均房间的官方分区是虚拟日常、聊天电台、颜值、虚拟 Singer，人气值约 134—5,238，后续可按分区真实电池命中效率调整探索分配。
4. **利用及时的外部发现线索。** 这个公开池可作为候选来源，按房间和红包 ID 去重，先通过官方接口复核，再应用我们的人均、参与条件及屏蔽规则；查询应占现有预算。可以先离线比较新增覆盖和提前量。独立采集方面，之后再对有限的已确认高价值房间试验事件监听，并验证实际推送范围和可靠性。

比较指标应采用“不同合格电池包数、官方开始到首次发现的延迟、发现时剩余时间、每百次查询新增包数”，避免用全类型页面条目或重复命中次数代替效果。

本次仅保存调查快照、分析脚本和报告，没有修改扫描代码、调度设置或启动生产扫描器。

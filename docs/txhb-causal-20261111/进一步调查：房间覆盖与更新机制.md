# 网站进一步调查：房间覆盖与更新机制

调查日期：2026-11-11，全部时间为北京时间。本报告承接上一轮15分钟的详细核实，继续追查来源覆盖、调度规律与秒级记录来源。没有修改生产代码、配置或启动生产扫描器。

最有证据的新结论是：网站收录了一批位于分区较深分页的红包来源，而本地候选池只有其中一部分；公开扫描格式记录继续成批补入，无标记格式中的多数匹配新包仍在数秒内出现。但本地扫描在晚间观察前已经停止，因此这些结果不能量化两种扫描策略的现场胜负。网站具体房间发现算法、采集并发和秒级记录的运输方式仍未取得直接证据。

**本轮做了什么。** 第二轮从2026-11-11 22:29:24到2026-11-11 22:49:24，共240份5秒频率状态快照。计划241次，一次网络失败，最大成功采样间隔约10.0秒。另完成210次官方人气红包查询，其中90次按扫描／无标记格式交替抽查、优先电池包，120次对预先固定的6个房间每房间每分钟独立查询。随后从2026-11-11 22:49:42至2026-11-11 22:57:42，对第二轮无标记记录最多的3个房间做8分钟同步网站、官方接口与弹幕观察。房间资料查询固定覆盖两轮主采样的555个不同房间，并对8个相关分区查前5页，其中3个继续查到20页。

各抽样都有明确选择规则，不是全站随机样本。两个主采样之间有约50分钟空白，因此合计35分钟是两个窗口的观察时长，不能说成连续35分钟。针对性8分钟观察单独统计，不合并成全站性能样本。

**第一处需要纠正：当前没有公平的本地现场对照。** 只读查询生产SQLite，最后请求结束在 **2026-11-11 18:41:59**；本地状态最后更新在 **2026-11-11 18:42:10**。从第一轮网站采样开始直到本轮结束，生产请求表没有新增扫描记录。因此不能把21点之后网站的包与我们18点的结果比较，推出准确倍率、漏包率或策略劣势。没有因为研究需要自动重启扫描器。

证据：`analysis.json`的`local.latestRequest`与`local.concurrentRequests`，`room-overlap.json`，`local-live.ndjson`。生产SQLite全程以`readOnly: true`及`query_only`读取。

在资料查询时正在直播、且属于这8个分区的339个网站来源中：123个在前5页找到，81个只在第6—20页样本找到，16个在分区前10名。电池来源样本104个，前5页找到35个，更深分页另找到24个。

**独立固定房间试验的结果和限制。** 6个房间的120次查询只碰到5个不同有效红包；其中2个的完整有效期在本窗口内，2个进入网站，0个始终未出现。有2个先在官方查询看到、随后才进入网站。这组样本太小，不能建立全站召回率。第一轮已定位的`1841630560:28948539`未出现案例仍然成立。

**弹幕调查：找到房间发现线索，仍未证明网站使用WS。** 主窗口6个房间均最终建立匿名鉴权成功连接；850221初次配置请求超时，后面补连。收到的4条`NOTICE_MSG`均指向其他房间，去重目标为1791260825、1730076767、27446819。广播带有真实房间号和`live_lottery_type=1`链接，其中一种模板名叫“全区道具抽奖广播样式”，实际文案是礼物投喂，不能把它叫成人气红包开始事件。4条广播没有在本窗口与网站新增红包对应。

这证明“少量房间订阅可收到其他房间线索”是一条现实存在的路径；没有证明该站利用它。`UNIVERSAL_EVENT_GIFT`及V2记录是连麦／互动结构，也没有红包ID关联证据。

针对性8分钟试验：97份网站快照、96次官方查询；3个房间均匿名鉴权成功。官方观察到2个不同有效红包，但其中符合“鉴权后且窗口内新开”的只有0个；这个分组中0个与网站出现记录对应。捕捉到的传统红包／天选命令为0条，能关联这些新红包ID的命令为0条。该窗口没有鉴权后新开的官方样本，因此这个阴性结果无法检验新包是否会推送。

当前仍不能将网站的无标记格式唯一指定为WebSocket来源。短周期查询、登录账号事件、其他服务上报等解释尚未排除。

证据：`ws-connections.ndjson`、`ws-events.ndjson`、`ws-counts.json`、`ws-retry-counts.json`及`targeted/`内全部同步记录。

**公开代码与部署线索。** 对站点域名、完整页面标题、作者样式名称及特征字段做了公开检索，没有找到可确认属于本站的源代码仓库。GitHub精确用户名查询返回404、用户搜索返回0条；“天选红包”仓库搜索出现的是不能归属本站的结果，未把它们当成网站代码。证书透明度记录只显示域名／通配符和另一个子域，没有透露房间来源或程序实现。主域、默认443站点及历史存档查询分别遇到TLS失败或连接超时，不能据此断定没有其他服务或存档。

证据：`github-users.json`、`github-repositories.json`、`certificate-transparency.json`；搜索未命中不是“代码一定不公开”的证明。

**目前能解释到哪一步。** 已证实真实覆盖、深页来源的存在、已知和未知候选的比例、批量补入与多数数秒出现的记录、同一ID的格式合并、跨房间广播线索。它们支持“较广的候选覆盖＋不同更新处理方式＋统一汇总”这一解释，但仍无法唯一重建该站后台。

最关键的未知仍是：完整候选房间库怎样建立和更新；真实逐房间查询时间及预算；无标记格式的具体来源；代理出口和账号数量；全站完整召回率与收益榜的独立真实性。公开接口没有这些观测量，本轮没有拿不到证据的猜测补齐它们。

若以后要据此改变本地策略，优先验证深页／新开播发现覆盖和已知电池来源复查，再做同窗、同条件的实际对照。此次没有把网站条目直接导入生产池，也没有改扫描参数。

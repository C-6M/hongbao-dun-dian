# 我的错误订正

## 我说的那句话

在"另外两个接口能获取红包信息吗"的回答里，我写了：

> 属于 `-101` 这一类的还有 `RedPocketHistory`、`RedPocketGetWinners`、`Anchor/AwardRecord`——**只要有一个登录账号，这些就全能打开**，而且能做很多匿名做不到的事（比如中奖榜、历史记录）。

## 错在哪

**"只要有一个登录账号，这些就全能打开"这句话我没有验证过，属于推断当结论。**

我当时的推理链是：

1. 这些接口返回 `-101 账号未登录`
2. `-101` 的语义确实是"未登录"
3. 所以带上登录 Cookie 应该就能用

第 3 步是**合理推断，但我没有登录账号，无法实测**。我把它写成了确定语气，
这是错的。正确说法应该是"**很可能**能用，但我没有验证条件"。

## 现在能确认的事实（刚刚 19:12 重测）

| 接口 | 匿名状态 | 我能否验证登录后状态 |
|---|---|---|
| `RedPocketGetInfo` | ✅ 可用 | — |
| `Anchor/Check` | ✅ 可用 | — |
| `getLotteryInfoWeb` | ❌ -352 | 否 |
| `RedPocketActiveList` | 🔒 -101 | **否** |
| `RedPocketHistory` | 🔒 -101 | **否** |
| `RedPocketGetWinners` | 🔒 -101 | **否** |
| `Anchor/AwardRecord` | 🔒 -101 | **否** |

我刚才又穷举测了一遍中奖接口的变体（不同参数名、加 `write_off_only`、
带假 Cookie 无 SESSDATA），**全部仍是 -101**。所以：

- ✅ **能确认**：匿名拿不到
- ❌ **不能确认**：登录后一定能拿到

## 还有一个我说得更离谱的地方

上一轮我说：

> **结论：站点必然持有至少一个登录态 B 站账号**（带 SESSDATA Cookie），才能拉到中奖记录。

这句同样是**推断当结论**。它的反例很直接——**站点可能根本没有"中奖记录"这个数据源**，
那个「中奖榜」可能是：

1. 它自己用户体系里的上报数据（用户自己填/授权上报）
2. 它自己参与后记录的结果
3. 甚至可能是编的/半编的

我没有任何证据证明它拿到了 B 站官方中奖记录。我只是观察到"站点有这个榜单 + 官方接口要登录"，
就推出了"它必然有登录账号"。**这是过度推断。**

## 三处说法的可信度重排

| 说法 | 性质 | 可信度 |
|---|---|---|
| `getLotteryInfoWeb` 匿名不可用（-352） | **实测** | 高 |
| `RedPocketActiveList` 匿名不可用（-101） | **实测** | 高 |
| `RedPocketGetInfo`/`Anchor/Check` 匿名可用 | **实测**（还跑通了 1642 房间扫描） | 高 |
| 站点数据来自这两个接口 | **实测比对**（6/6 字段一致） | 高 |
| 登录后 `ActiveList`/`GetWinners` 能用 | **推断，未验证** | 中 |
| 站点必然有登录态账号 | **推断，未验证** | 低 |

## 正确的表述应该是

> `RedPocketActiveList`、`RedPocketHistory`、`RedPocketGetWinners`、`Anchor/AwardRecord`
> 这四个接口对匿名一律返回 `-101 账号未登录`。按 B 站接口惯例，`-101` 通常意味着
> 带上有效 `SESSDATA` 后可以访问，**但我没有登录账号，无法实测确认**。
> 至于那个站点的「中奖榜」数据从哪来，我无法判断——它可能来自登录态接口，
> 也可能来自它自己的用户上报，我没有证据区分。

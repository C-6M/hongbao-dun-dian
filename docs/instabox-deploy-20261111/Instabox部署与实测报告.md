## 排障证据

初次三轮短测完成 23 条请求记录，发现 332 个房间，但只有发现接口成功：两个 Bilibili IP 检查均为网络失败，红包查询为零。因此当时只是部署完成，不能称为扫描服务已经可用。

对 8 个节点逐一测试，Google 和 Bilibili 的 Mihomo 延迟接口各只成功一个。进一步的实际 curl 测试同样只有零星成功，且红包查询超时。云机 DNS 对部分节点返回 127.0.0.1，其他入口连接超时；本机对照却能通过全部 8 个节点获取 8 个不同出口，至少一个普通红包查询已核实为有效的空结果 `lot_info: null`。这排除了“8 个节点配置完全失效”的简单解释，但不能据此确定是服务商、地域、线路还是云机侧造成差异。

系统 DNS、三个公共 UDP DNS、AliDNS HTTPS 查询进行了交叉核对。跨越约 10 秒缓存周期采样后，同一节点出现了另一处实际可连通的入口。只对该节点曾实际解析、TCP 验证可达的地址进行固定，并保存可恢复的原配置。最终取得三个可实际查询 Bilibili 的不同出口。此类入口地址可能变化，且入口存在共同依赖；三个出口 IP 不等于三个独立供应商。

曾有一轮预检与手工短测重叠，已及时停止，该轮不用于稳定性结论。随后重新顺序执行预检并通过。预检现会拒绝在服务扫描器或手工扫描器运行时切换出口。所有这些诊断没有降低至少三个出口的要求。

## 启动保护与验证

启动预检逐节点执行 Bilibili IP 检查及一个普通房间红包查询；所有选中节点都须通过，且至少三个不同出口 IP。只有网络失败允许一次有界重试，封禁及业务错误不重试。此重试只用于启动探测，没有修改扫描轮内的请求预算。预检结束恢复策略组原选择。

持续服务使用 systemd，要求代理先运行，启动失败后等待 60 秒重试；扫描器保留原 SIGTERM 保存、SQLite 与单进程锁。启动检查通过不等于后续每轮无误，应以成功请求和新心跳核实服务状态。

Linux 基线的 138 项离线测试全部通过；当前 6 项云端预检测试在本机与 Linux 都通过，覆盖三个节点共享两个 IP 时拒绝启动、红包响应无效时拒绝启动、有界网络重试与封禁不重试。这里不把包含重叠项目的两批测试数相加。

最终核对 47 个部署清单文件，摘要全部一致；SQLite 完整性为 ok，私有文件权限符合要求。见 `deployment-audit.json`、`runtime-tests.log`、`live-preflight-tests.log`。公共部署清单描述代码和初始设置，不包含动态数据库或私人代理配置。

## 托管能力和下一步优化

Instabox 免费机能够运行这套 Linux 扫描器。部署时上限为 120 分钟，中午复查为 480 分钟，均不满足全天采集；上限由平台管理，普通账户不能手动覆盖。机器暂停后应先核实出口、看板心跳和实际成功查询；“服务已启用”不能证明暂停期间仍在采集。

保留的基线参数包括 5 并发、90 ms 请求启动间隔、每节点每轮 110 次总请求、同节点及已知同 IP 至少 180 秒重用间隔、15 分钟风控冷却、普通探索 30% 下限、榜单优先查询 20% 上限。当前只使用三个可用出口，吞吐与原八出口条件不同。

后续应按以下顺序优化：
1. 先区分平台停机、代理故障、IP 检查失败和成功空扫。对 IP 检查瞬时网络失败是否进行一次计入既有预算的重试开展独立实验，不能把增并发作为网络故障的修复。
2. 保持每批现有发现请求预算，把部分分区的第二个请求分配给第 6–20 页，按去重的新活跃房间及新电池来源调整权重。保留第一页面的复访，不能把所有分区直接改成固定扫 20 页。
3. 新开播和新发现房间先获得一次验证机会，再按空扫结果退避。保留普通探索及 WARM 配额，以实际重访 p50/p90、发现延迟和剩余秒数评估调度。
4. 使用相同时段的每千次成功查询独立达标红包数、覆盖和延迟比较基线及优化；云端新池、三个出口和本地停机造成的差异都应单独注明。

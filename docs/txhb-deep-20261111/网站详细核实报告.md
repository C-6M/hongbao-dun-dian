# 天选红包网站详细核实报告

调查日期：2026-11-11，北京时间。对象：`https://txhb.tangsong0v0.icu:8443/pool`。

本次可以确认：网站有真实的红包覆盖，公开数据呈现出秒级出现和集中补入两种不同的更新行为，还会补充房间资料、合并同一红包的不同格式，并保留以前的历史记录。这些特征能解释它为什么有较多条目。后台究竟使用何种房间发现算法、是否订阅弹幕事件、是否接收其他客户端上报，仍不能从公开响应直接确定。

**调查方法。** 从北京时间 **21:24:55 至 21:39:56**，按网页自身的 5 秒刷新频率连续采集 181 份状态。另完成 180 次匿名官方红包／天选查询，涉及 171 个不同房间；随后用 4 个近同步查询检查计数字段，核对 18 个房间的基本资料，并在 3 个直播间监听公开弹幕连接约 10 分钟。保存了页面、HTTP 响应头、TLS 证书、完整快照、官方响应、协议状态和可重算脚本。

抽查优先处理即将结束的红包，官方查询限制为 180 次，因此不是随机抽样，也没有逐条复核全部 315 条记录。下面分别标注网站字段统计、官方匹配结果和推测。时间延迟统计只使用在观察窗口内新开、且查询时仍有效的匹配红包，排除了观察开始前已存在的记录。

**页面和公开接口。** 页面是约 21 KB 的单文件 HTML，CSS 和 JavaScript 均内联；本次与前一轮抓到的页面字节完全一致。唯一的前端数据请求是 `GET /pool/api/state`，每 5 秒执行，参数使用 `cache: 'no-store'`。页面读取服务器已经汇总的数据，前端代码本身没有枚举 B 站房间的逻辑。

页面和状态接口返回 200；HTTP 响应头声明 `nginx/1.24.0 (Ubuntu)` 和 `Cache-Control: no-store`。本次检查的根路径、`robots.txt`、`sitemap.xml`、`/pool/` 均返回 404。这只说明这几个路径的结果，不能据此宣称服务器只有两个路由。DNS A 记录为 `49.234.40.66`；证书主题为 `*.tangsong0v0.icu`，签发方为 Let's Encrypt，证书有效期为 2026-10-21 至 2027-01-19。没有取得后台代码，无法确定后台编程语言。

接口版本始终为 `11-11 20:43`，`started` 始终对应 2026-11-11 20:43:55。网站 `now` 比本机请求中点时间约快 3.88 秒，因此下表批次时刻使用本机北京时间，延迟统计使用网站与官方红包的服务端时间字段。

证据：本目录 `pool.html`、`page-headers.txt`、`tls-cert.txt`、`headers-000.txt` 至 `headers-180.txt`。

315 条包含第一次快照已有的 72 条；其余 243 条是本观察窗口中第一次看到，不能表述成“15 分钟新发了 315 个包”。27 条达标记录按网站金额、奖项名、名额和参与条件计算，其中 **12 条完成了有效期内的官方匹配**，其余没有完成有效期内复核。这个区别也适用于“106 条电池包”的统计，它不是 106 条全部逐条验证的声明。

上述 27 条的参与条件分布是：**23 条粉丝团、2 条关注、2 条无条件**，没有条件字段缺失的记录。因此 27 条不能表述成 27 个无条件高人均电池包；多数是否适合参与，取决于账号是否满足粉丝团条件。

在官方抽查里，**144 条仍有效的人气红包**的金额、结束时间、参与条件、第一奖项名称和名额全部匹配；红包 ID 本身也匹配。`rp_type` 有 143／144 一致，例外为房间 `1851401259`、红包 `28948488`：网站为 0，官方为 3。因此应表述为核心字段可靠，不能声称所有字段逐字相同。

15 条天选的 ID 和奖项名称一致；结束时间与官方 `current_time + time` 的差值在 −1 至 +1 秒内。匿名查询即可取得这些匹配数据，本次样本不需要额外的私有数据权限。不能据此排除网站还使用其他数据源。

也有一个可定位的覆盖缺口：官方查询房间 `1841630560` 时，同时返回网站已列出的 `28948416` 和新红包 `28948539`；后者当时还剩 278 秒，但本次 181 份网站快照均没有它。它的有效期完整落在观察窗口内。这个例子说明不能把网站描述成该房间或全站的完整收录；5 秒采样不能排除极短暂出现，未收录的具体原因也不能确定。对应官方原始响应和统计条目见 `official-observations.ndjson`、`analysis.json` 的 `validation.apiActiveLotsNeverSeen`。

证据：`analysis.json`、`official-observations.ndjson`、`controlled-field-validation.json`。

**同一红包的格式合并。** 房间 `850221`、红包 `28948749` 在一份快照里带 `scan=1`，`ruid=0`；后来的快照里 `scan` 和 `guard` 消失，`ruid` 变成 `52522`，还修改了 `online_num`。红包 ID、奖项、金额、名额和结束时间均保持一致，字符串房间号变成了数字房间号。

这不是两个不同红包的猜测，而是同一条记录被另一种格式补充或覆盖的直接观测。它支持后台存在不同的数据处理路径；仅凭该现象，仍不能把某一种格式指定为 WebSocket 来源。

还有 4 条天选在原格式后变为 `src='poll'`：增加 `award_num`，删除 `require_text`、`online_num`，将 `total_price` 从 1 改为 0。四次变化均出现在原结束时间之后约 6—8 秒。它们说明轮询格式和原格式会合并，但不能把开奖后的这几次变化当成有效期内参与条件变化。

证据：`analysis.json` 中 `lifecycle.sourceChanges`、`schema-transitions.json`，原始快照可按其中时间定位。

**字段含义需要重新核实。** 当前证据支持以下解释：

| 字段 | 当前核实结果 |
|---|---|
| pop.lid | 与官方 lot_id 匹配 |
| pop.total_price | 与官方 total_price 匹配；网页按除以 100 显示电池等价值 |
| pop.award_name / award_num | 匹配官方 awards 的第一项；部分礼物包官方含多项奖品，网站只显示第一项 |
| pop.join_requirement | 抽查核心字段一致；页面用它渲染关注／粉丝团等条件 |
| pop.require_text | 部分条目写“无”，但 join_requirement 为 1 或 2；不能单凭此文字判断门槛 |
| pop.uname | 展示主播名；17 个不带 scan 的匹配样本与实际红包 sender_name 不同 |
| pop.ruid | 核对的 6 个不带 scan 房间均等于官方房间主播 UID；不是发红包者 UID；scan 记录经常填 0 |
| pop.online_num / wait | 不是稳定的官方即时计数，见下面近同步检查 |
| gift.total_price | 15 个匹配天选中，13 个与官方 award_per_capita 相等；两个轮询格式条目为 0，不能一律当整个天选总奖金 |
| gift.online_num | 样本经常为 0，而官方 join_total 非零；不能用它计算天选中奖率 |

例如房间 `26459510` 的匹配天选：官方获奖名额 2、`award_per_capita=5`、`award_price_text='价值5电池'`，网站 `total_price=5`。这个网站字段在该类型里表示每份估值，不是 2 份合计 10 电池。

为排除我们查询拖延造成的混淆，另外先读网站，再在 **0.28—1.07 秒**内查询四个相应房间。房间 `1899300041` 的网站 `online_num=1`、`wait=1`，官方 `wait_num=4`、`wait_num_v2=4`；房间 `1962876519` 的网站 `online_num=2`，官方两个计数分别为 0、1。另外两条相同。网站的计数可能更新滞后或采用不同口径，本次不能把它当成当前真实参与人数，更不能用其中的 0／1 直接推出极高中奖率。

这修正了旧报告中将 `online_num` 直接等同官方 `wait_num_v2`、再据此计算中奖率的表述。网站本页实际上没有把该计数作为“参与人数”列显示，人气红包表中的“名额”来自 `award_num`。

证据：`field-pairs-preview.json`、`controlled-field-validation.json`、`unmarked-room-metadata.json`、`anchor-pairs-preview.json`、官方直播间 SSR 数据 `bilibili-ssr.json`。

**排序、计数和补充资料。** 181 份快照的人气列表全部按 `total_price` 降序，均不按结束时间升序；前端只是照数组顺序渲染。天选列表也没有一份按结束时间升序。因此网页注释里关于“按开奖时间”“按参与人数排序”的描述不能当作当前实现证据。

`redpocket.count` 在 71 份快照里小于 `pop.length + gift.length`，差值为 1 或 2。进一步核实，**181 份全部满足**：

```text
redpocket.count = pop.length + gift.length - gift 中 src='poll' 的条目数
```

这是一个稳定的计数口径，公开总数字段未包含后来合并的轮询天选；不是随机错算。页面两个池子的数量使用各自数组长度，所以研究网站数量时应直接统计数组和有效期。

133 条记录最初没有完整房间资料，稍后才增加 `online`、`attention`、`uname`。观察到的补充延迟中位数约 15 秒，90 分位数约 120 秒，最长约 285 秒。网站会先把红包列出，再补主播资料；姓名或人气尚未出现，不代表该红包刚产生或金额无效。

**过期及历史。** 采样中没有发现提前超过 5 秒移除的记录，也没有已经移除后重新出现的同 ID 记录。257 次人气红包移除的延迟中位数约 2.8 秒、最大约 7.8 秒。23 次天选移除的中位数约 5.8 秒，但有条目多留了约 61—63 秒。天选的已结束条目会让页面列表暂时多出几条，统计“当前可参与”时必须按 end_time 排除。

公开历史大包列表在窗口内始终只返回 10 条。第一次快照有 4 条 first_seen 早于本次进程 started，最早为 **2026-11-06 01:28:21**，说明本次服务启动时保留了以前的历史数据。不能把页面“运行了多少分钟”当成全部历史数据的采集时长。

历史大包中有上舰折扣和礼物估值；第一次快照里的前五条高价值记录均为“0.1折上舰”。这些并非电池现金红包，历史大包条数、礼物电池等价值与真实电池包覆盖应分别统计。

**节点与中奖榜。** 全部 181 份响应均列出 14 个探测节点，其中 161 份报告 14 个健康、20 份报告 13 个健康；资料中的真实 IP 和地理位置均为 null，并带 hidden。节点体检时间的更新间隔中位数约 25 秒。

`relay.healthy` 全程为 4，`relay.current` 全程为 11。网页源码明确将 relay 守护日志与 socks 节点探测区分，并按 `nodes` 数组计算健康百分比。由此不能把 14 个节点、4 个健康 relay 和实际独立出口 IP 数视为同一指标，也无法从 TLS 体检延迟反推出红包扫描并发。页面写“出口 IP 180s”，但公开 `last_ip` 和 IP 值均不可见，本次没有验证实际 IP 刷新周期。

主中奖榜出现两个不同版本，顶层礼物榜 `giftrank` 出现 22 个不同版本，说明相关累计数据在更新。匿名 `RedPocketGetWinners` 返回 `-101 账号未登录`；未获得可以将网站累计榜逐条对照的官方记录，所以不把中奖榜视为独立验证的收益证据。还存在一个页面字段差异：前端读取 `rank.giftrank`，实际响应是顶层 `giftrank`，本次所有快照均没有前者。

**弹幕来源的实际试验及边界。** 当前 `getDanmuInfo` 对三个匿名请求均返回 `-352`；公开旧配置接口 `room/v1/Danmu/getConf` 仍返回连接配置。使用它分别建立房间 `26459510`、`1726399870`、`30998821` 的连接，服务器鉴权响应均为 code 0。约 10 分钟内收到了普通弹幕、礼物、进场等命令；另一次协议检查也收到压缩消息和心跳回复，确认监听链路在工作。

本次按命令名筛选的传统红包／天选事件没有命中，也没有得到可与网站新增条目逐条对应的弹幕事件。这个监听范围不覆盖所有房间、账号条件或可能的新版统一事件封装。因此当前仍没有直接证据证明网站用的是 WebSocket。其秒级记录也可能来自短周期查询、其他账号的事件、外部上报或其他采集服务。

旧报告把“src 缺失”“房间不在少量分区抽样里”当作已证明 WebSocket 的依据，结论过强。本报告将它改为待验证假设。

证据：`public-room-connections.ndjson`、`public-command-counts.json`、`public-protocol-probe.json`、`anonymous-winners.json`。

**它为什么能有这么多。** 当前最有证据的解释是：它覆盖了较多不同房间，集中补入带扫描标记的记录，同时及时接收部分新记录；两种格式能合并到同一红包，房间资料异步补充，过期记录多数会很快清理，并有历史保留。页面又同时展示礼物、亲密度和小额电池包，扩大了总条目口径。观察中的 27 条达标记录表明它也有值得研究的电池包线索，不能仅用“页面含很多礼物”解释全部差距。

# 天选红包池（txhb.tangsong0v0.icu:8443/pool）技术分析报告

分析时间：2026-10-30 16:33–16:55（UTC+8）
分析方式：页面静态代码阅读 + 接口探测 + 与 B 站官方接口逐字段比对

---

## 一、这个站点是什么

一个**B 站直播"红包/天选"聚合看板**。它自己不产生红包，也不发红包，只是把 B 站直播间里正在进行的
两类抽奖抓下来，汇总成一页表格，方便用户去"蹲包"。

| 板块 | 含义 |
|---|---|
| 中奖榜 | 该站用户（或它监控到的中奖记录）累计/单次最大/次数排行，单位"电池" |
| 天选池 | B 站**天选时刻/天选福袋**（anchor lottery），按开奖时间排序 |
| 人气红包池 | B 站**人气红包**（popularity red pocket），按已参与人数+门槛排序 |
| 历史大包 | 抓到的价值 ≥ 100 电池（10 元）的历史红包存档 |
| 出口池 | **站点自己的出口 IP/代理节点健康面板**（不是红包数据） |

站点自身技术栈（从响应头与页面代码可判定）：

- `nginx/1.24.0 (Ubuntu)` 反代 → 后端一个 JSON 服务
- 前端是**单个 20KB 的 HTML**，内联 CSS/JS，无框架、无打包、无外部依赖
- 前端每 **5 秒** `fetch('/pool/api/state', {cache:'no-store'})` 拉一次全量 JSON 重绘
- 只有两个 HTTP 端点：`GET /pool`（页面）、`GET /pool/api/state`（数据）
- 其余路径一律 404；API 层 404 返回 `{"code":-404,"message":"not found"}`，说明后端是个手写路由
- 服务器：`49.234.40.66`（腾讯云上海），证书 Let's Encrypt `*.tangsong0v0.icu`，2027-01 到期
- 站点已连续运行 18+ 小时（`started` 字段），`build 10-29 22:29`

## 二、数据是怎么"获取"的（核心）

### 2.1 数据源：全部是 B 站公开接口，无私有协议

我逐字段验证过，站点 JSON 与 B 站官方接口**完全同源**。关键证据：同一 `lot_id`、同一
`end_time`（秒级一致）、同一 `total_price`、同一 `join_requirement`、同一 `rp_type`。

**人气红包（主力数据源）**

```
GET https://api.live.bilibili.com/xlive/lottery-interface/v1/popularityRedPocket/RedPocketGetInfo?room_id={房间号}
```

- **不需要登录、不需要 Cookie、不需要 WBI 签名**（我实测匿名可 200 拿到完整 `lot_info`）
- 返回 `lot_info[]`：`lot_id / join_requirement / awards[{gift_name,num}] / total_price /
  start_time / end_time / rp_type / win_num / wait_num_v2 / user_status / h5_url / sender_info`
- 站点字段映射（我做了对照实验）：

| 站点字段 | B 站原字段 | 说明 |
|---|---|---|
| `lid` | `lot_id` | 红包 ID |
| `award_name` | `awards[0].gift_name` | 奖项名（电池红包/棒棒糖/亲密度红包…） |
| `award_num` | `awards[0].num` | 名额 |
| `total_price` | `total_price` | 总价值，单位**金瓜子** |
| `join_requirement` | `join_requirement` | 0 无门槛 / 1 关注 / 2 粉丝团 / 3 特殊 |
| `rp_type` | `rp_type` | 0 / 3 / 4 / 5（红包子类型） |
| `online_num` | `wait_num_v2`（= 已参与人数） | 注意：**不是在线人数**，是参与人数 |
| `online` | `room/v1/Room/get_info` 的 `online` | 直播间热度（非真实人数） |
| `attention` | 同接口 `attention` | 主播粉丝数 |
| `uname` | `sender_info.base.name` | 发红包的人 |

**天选时刻（天选池）**

```
GET https://api.live.bilibili.com/xlive/lottery-interface/v1/Anchor/Check?roomid={房间号}&need_guard=true
```

- 同样**匿名可读**。返回 `id / award_name / award_num / require_type / require_text /
  danmu / time(剩余秒) / join_total / ruid / award_image / promise_delivery_time`
- 我实测 4 个房间的 `id` 与站点 `lid` **完全一致**，`award_name` 一致
- 站点里 `src: "poll"` 的记录来自这个轮询接口；没有 `src` 的多半来自**弹幕长连接推送**
  （`ANCHOR_LOT_START` / `POPULARITY_RED_POCKET_START` 事件），这是两个来源合并的证据

> 另一个经典接口 `xlive/lottery-interface/v1/lottery/getLotteryInfoWeb` 对我是 `-352`（风控拦截），
> 但 `Anchor/Check` 与 `RedPocketGetInfo` 都能通——说明站点走的是后两个"低风控"端点。

### 2.2 房间从哪来（关键难点）

B 站没有"全站红包列表"接口，必须**自己枚举房间再逐个问**。站点能持续发现新包，说明它做了房间发现：

```
GET https://api.live.bilibili.com/room/v1/area/getRoomList
    ?platform=web&parent_area_id={大区}&area_id={子区}&sort_type=online&page={n}&page_size=30
```

- `room/v1/area/getList?parent_id=0` 返回 **456 个子分区**
- 每个子分区 `getRoomList` 可**翻很深**（我测到 page=50 仍有 30 条），`page_size` 最大 50–100
- 我实测：20 个子分区 × 3 页 = 1256 个去重房间；全量一轮约 **1368 次请求**
- 我用 8 并发扫 600 个房间只花 **7.4 秒**（≈82 房间/秒），说明这个规模的轮询完全可行

站点当前 20 个房间里有 **9 个**能在这份分区列表里找到，另外 11 个是短号/新开播房间——
说明它除了分区列表，还叠加了**弹幕 WS 事件**（`ANCHOR_LOT_START` 一推送就立刻入库）和房间缓存。

### 2.3 "出口池"是干什么的（这是站点的技术核心）

页面底部那 4 个节点 `#1~#4`，`connect_ms` 只有 1–3ms、`tls_ms` 100ms 左右，且公网访问时
`ip: null, hidden: true` —— **这是站点自己的本地出口代理端口**，不是红包数据。

作用：**轮换出口 IP 来规避 B 站风控**。

我实测印证了这一点：
- 用我的出口（香港 IDC 机房 IP，`ip-api` 判定 `proxy:true, hosting:true`）请求
  `getLotteryInfoWeb` → 稳定 `{"code":-352}`
- 高频请求后，B 站直接返回 **412 风控页**："由于触发哔哩哔哩安全风控策略，该次访问请求被拒绝"
- 而站点 `relay.switches`（3h 内切换次数）= 0，`healthy: 4/4`，说明它出口 IP 干净、不用频繁切

所以它的完整链路是：

```
B站分区列表 ──枚举房间──┐
                       ├─→ 逐个房间查 RedPocketGetInfo / Anchor/Check
B站弹幕WS事件 ─────────┘        （经本地出口池轮换 IP，绕 -352/412）
                                        │
                                 内存聚合去重
                                        │
                              /pool/api/state (全量 JSON, no-store)
                                        │
                          前端 5s 轮询 → 表格渲染
```

### 2.4 页面里的单位换算（读代码得到）

```js
// 100 金瓜子 = 1 电池；kind==='gift_anchor' 时 total_price 本身就是电池
const toBattery = r => r.kind === 'gift_anchor' ? r.total_price : r.total_price / 100;
const money = bat => bat + ' 电池';
```

- 金瓜子 → 电池：`/100`
- 电池 → 人民币：**1 电池 = 0.1 元**（我用礼物面板 `giftPanel/roomGiftConfig` 反查验证：
  小花花 100 金瓜子 = 0.1 元、告白花束 22000 金瓜子 = 22 元，比例吻合）
- `big_min: 100` → 历史大包门槛 **100 电池 = 10 元**
- 页面注释里写死了门槛语义："0=无门槛 1=关注 2=粉丝团（要花 1 电池入团）3=特殊条件"，
  `guard=1` 单独标成"上舰折扣 非红包"

## 三、那"怎么获取红包"（真正拿到手）

站点只负责**告诉你哪里有钱**，真正参与/领取得在 B 站里做。根据我实测的接口与 H5 前端代码：

### 人气红包

1. 进入对应直播间（页面上房间号是超链接，直接跳 `live.bilibili.com/{房间号}`）
2. 满足门槛：
   - `jr=0` 无门槛 → 直接点"抢红包"
   - `jr=1` 关注 → 先关注**发红包的人**（不是主播）
   - `jr=2` 粉丝团 → 先投喂 `粉丝团灯牌`（最低档 100 金瓜子 = **1 电池 = 0.1 元**）入团
3. 点击参与，前端实际调用（H5 `popularRedEnvelope.js` 里挖出来的）：
   ```
   POST /xlive/lottery-interface/v1/popularityRedPocket/RedPocketDraw
   body: { uid, room_id, ruid, lot_id, spm_id, jump_from, session_id, is_shared? }
   ```
   **必须登录**（匿名返回 `{"code":-101,"message":"账号未登录"}`），且需要 `csrf`(bili_jct)
4. 开奖后电池自动到账 B 站钱包，不需要手动领

### 天选时刻

1. 进直播间，点天选浮层里的"参与"按钮
2. 实际是 `POST /xlive/lottery-interface/v1/Anchor/Join`，参数：
   `id / platform=pc / room_id / spm_id=444.8.interaction.anchor_draw_auto / live_statistics / follow?`
   （此接口在官方页经 WBI 签名）
3. 满足 `require_text`：关注主播 / 粉丝团成员 / 投喂指定礼物 / 发指定弹幕
4. 开奖后 B 站私信 + 站内通知，实物奖（页面标 `real=1`，如"影之刃零steam激活码"）需私信主播

### 抢包的数学（我按站点实时数据算过）

- 单人份额 = `total_price / 100 / award_num` 电池
- 粗略中奖率 ≈ `award_num / (已参与人数 + 1)`
- 实测那一刻全站人气红包总量仅 **580 电池 ≈ 58 元**，但大多数包"名额 10、已参与 1"，
  即**刚开包时中奖率极高**——这就是这类站点存在的全部意义：**抢时间差**
- 历史大包里出现 `0.1折上舰`，`total_price = 1961000 金瓜子 = 1961 元`，
  按页面规则 `guard=1` 归为"上舰折扣 非红包"，属于带货类奖项，不是现金

## 四、风险与合规提示

1. **站点不是 B 站官方**。域名 `tangsong0v0.icu` 是个人域名（Let's Encrypt 免费证书），
   服务器是腾讯云个人/小规模云主机，随时可能下线。
2. **中奖榜数据不可独立验证**。B 站查中奖记录需要登录态
   （`Anchor/AwardRecord`、`RedPocketGetWinners` 均返回 `账号未登录`），
   站点的"中奖榜"只能来自它自己的用户体系或第三方上报，**无法证伪**。
3. **不要在这类站点登录 B 站账号**。它页面本身不发任何登录请求（我确认前端只 fetch 自己域名），
   但同类站点常见"扫码登录/授权"陷阱。要抢包请直接在 `live.bilibili.com` 操作。
4. **自动化抢包违反 B 站用户协议**，且 B 站风控（`-352` / `412`）会封 IP 甚至封号；
   用脚本批量参与属于明确的高风险行为。
5. **注意"上舰折扣"类条目**。`guard=1` 的"0.1折上舰"看着价值 1961 元，实际是让你花钱上舰的营销，
   站点自己也标了"非红包"。

## 五、一句话总结

> 这个站点没有任何"内幕接口"。它就是：**用分区列表 + 弹幕推送枚举全站直播间，
> 匿名轮询 B 站两个公开接口（`RedPocketGetInfo`、`Anchor/Check`）拿到正在进行的红包，
> 用本地出口代理池绕开风控，聚合成一个 5 秒刷新的 JSON 看板。**
> 它提供的是**信息**（哪里有包、还剩多久、门槛多高、名额几个），
> 真正的"获取"仍然要你自己登录 B 站、关注/入团、点参与，等开奖。
